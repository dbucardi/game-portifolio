# Dragons of Mugloar: requirements

This document says **what** the solution must do, not **how**. It names no language, framework or library. Any stack that meets every requirement here is a valid solution. The chosen stack and design are in [PLAN.md](PLAN.md).

**Keywords:** **MUST** is required for acceptance. **SHOULD** is expected unless there is a documented reason not to. **MAY** is optional or a bonus.

**IDs** are stable. Code, tests and the README can refer to them (for example `BOT-05`), so traceability survives a change of stack.

## 1. Glossary

| Term                    | Meaning                                                                                                                                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Game**                | One session identified by a `gameId`, with lives, gold, level, score and turn.                                                                                                                      |
| **Ad**                  | A task offered by the game: id, message, reward, expiry in turns, a probability label, and an optional encryption flag.                                                                             |
| **Probability label**   | A text label such as "Piece of cake" or "Suicide mission" that hints at the chance of success.                                                                                                      |
| **Item**                | Something sold in the shop. A healing potion gives +1 life; the other items raise the level.                                                                                                        |
| **Strategy**            | The policy that decides which ad to solve and what to buy each turn.                                                                                                                                |
| **Runner**              | The loop that drives one game from start to game over using a strategy.                                                                                                                             |
| **Run**                 | One bot-played game managed by the bot service. It has a run id, a status (`running` / `stopping` / `stopped` / `finished` / `failed`), the latest game state and an event history.                 |
| **Bot service**         | The backend: an HTTP API that starts, stops and reports on runs and benchmarks.                                                                                                                     |
| **Benchmark**           | Several games played in a row to measure how reliably the bot scores.                                                                                                                               |
| **Expected value (EV)** | The average gold an ad is worth to the player: `p × reward − (1 − p) × lifeCost`, where `p` is the estimated success chance and `lifeCost` is the gold value of the life lost on failure (CORE-06). |
| **Advisor**             | The opt-in view in manual play that shows the EV and trap tag of each ad (WEB-07). It is advice only.                                                                                               |
| **Quest**               | The player-facing name for an ad in manual play.                                                                                                                                                    |
| **Suspense phase**      | The short, animated wait in manual play between choosing a quest and seeing its result. The API call has already been made, and the web app holds back the result.                                  |
| **Reveal**              | The moment the result of a quest or purchase is shown, with what changed.                                                                                                                           |

## 2. External API contract

The solution MUST work with the public API at `https://dragonsofmugloar.com/api/v2`. These facts were checked on 2026-11-05, and are the reference for fakes used in tests.

| ID     | Operation  | Request                                 | Successful response                                                             |
| ------ | ---------- | --------------------------------------- | ------------------------------------------------------------------------------- |
| API-01 | Start game | `POST /game/start`                      | `gameId, lives, gold, level, score, highScore, turn`                            |
| API-02 | List ads   | `GET /{gameId}/messages`                | list of `adId, message, reward, expiresIn, encrypted (null\|1\|2), probability` |
| API-03 | Solve ad   | `POST /{gameId}/solve/{adId}`           | `success, lives, gold, score, highScore, turn, message`                         |
| API-04 | List shop  | `GET /{gameId}/shop`                    | list of `id, name, cost`                                                        |
| API-05 | Buy item   | `POST /{gameId}/shop/buy/{itemId}`      | `shoppingSuccess, gold, lives, level, turn`                                     |
| API-06 | Reputation | `POST /{gameId}/investigate/reputation` | `people, state, underworld` (uses up a turn)                                    |

Known behaviour:

- **API-18:** `POST /{gameId}/investigate/reputation` returns only `people, state, underworld`, as whole numbers, and no `turn`. It uses up one turn all the same: a purchase made right after it came back as turn 2 (checked 2026-11-08).
- **API-19:** the `highScore` field in the start and solve responses is always `0`. It did not change after a full game that ended with 1035 points, and it was still `0` at the start of the next game (checked 2026-11-08). The solution does not use it (WEB-18).
- **API-10:** error responses have an HTML or plain-text body, not JSON. Examples are 400 for a bad ad id and 404 for an unknown game. Calls also fail after game over; confirm the exact status code.
- **API-11:** `encrypted = 1` means the ad's `adId`, `message` and `probability` are Base64-encoded. `encrypted = 2` means they are ROT13-encoded. Confirm both against live samples.
- **API-12:** `reward` may arrive as a number or as a numeric string.
- **API-13:** the API allows cross-origin requests from any origin, so a browser can call it directly.
- **API-14:** every solve and every purchase uses up one turn. Ads expire after `expiresIn` turns.
- **API-15:** a new game starts with 3 lives and 0 gold, level, score and turn.
- **API-16:** shop items:
  - `hpot` costs 50 and gives +1 life;
  - `cs`, `gas`, `wax`, `tricks` and `wingpot` cost 100 each;
  - `ch`, `rf`, `iron`, `mtrix` and `wingpotmax` cost 300 each.
- **API-17:** probability labels seen so far: _Piece of cake, Walk in the park, Sure thing, Quite likely, Hmmm...., Gamble, Risky, Rather detrimental, Playing with fire, Suicide mission, Impossible_.

- **API-20:** steal quests ("Steal ... delivery ...") stop working after a few successes, whatever their probability label says. In 40 games (1,725 solves, checked 2026-11-09) a steal succeeded 0.97, 0.95, 0.94 and 0.93 of the time as the 1st to 4th, then 0.88 as the 5th, 0.33 as the 6th, 0.11 as the 7th, and 0.06 or less after that. The count of earlier steals is what matters, not the turn or the level. Steals pay a mean reward of 142, against 78 for escort quests and 34 for advertisement quests.
- **API-21:** reputation does not recover (checked 2026-11-09, 8 games). After the cliff, 36 steal probes over up to 60 turns of safe quests succeeded 0.13 in the first 12 turns and never after. The `state` value from `investigate/reputation` is about −10 or lower at the cliff, falls by about 2 per steal, and rose by about 1.7 in 40 turns.
- **API-22:** no shop item changed the success rate beyond the label. In 871 "Help defending ..." quests, with 500 to 800 samples per item, the success rate matched the label for each of the ten upgrades (difference within ±0.02). Every upgrade only raises `level`, by 1 or sometimes 2.
- **API-23:** "Create an advertisement campaign ..." quests fail considerably more often than their probability label suggests (reported from play 2026-11-10; not yet measured by the benchmark). A trace of 36 bot games (checked 2026-11-10) did not confirm it: 38 "Piece of cake" campaigns succeeded 0.97 and 36 "Walk in the park" ones 0.83.
- **API-24:** the game changes by turn, not by level (checked 2026-11-10, 36 games, 2,650 solves). Before turn 22 it offers only small quests (help, sell, escort, advertisement, steal) paying 15 to 75. "Help defending ..." quests first appear between turns 22 and 27 at every level, and from turn 40 they are the only quests on offer. Their labels get worse with the turn: no "Piece of cake", "Walk in the park" or "Sure thing" ad is offered after turn 60, and from turn 80 almost every ad is "Suicide mission" or "Impossible".
- **API-25:** level raises the reward, not the odds (API-22). Between turns 20 and 59 a defend quest pays about 80 + 6 to 8 gold per level. The 100-gold items always raise `level` by 1 (590 purchases) and the 300-gold items by 2 (310 purchases), so the 300-gold items cost more gold per level but fewer turns (API-14).

## 4. Backend bot program

| ID     | Level        | Requirement                                                                                                        | Acceptance criteria                                                 |
| ------ | ------------ | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| BOT-01 | MUST         | Starts a new game.                                                                                                 | One game start call per game played.                                |
| BOT-02 | MUST         | Fetches the current ads.                                                                                           | Ads are fetched at the start of each loop iteration.                |
| BOT-03 | MUST         | Picks the best ad according to the strategy and solves it.                                                         | The solved ad is the strategy's top choice.                         |
| BOT-04 | MAY → SHOULD | Buys items when the strategy decides it improves the odds.                                                         | Purchases appear in the log, and gold and level or lives update.    |
| BOT-05 | SHOULD       | When lives are low and it can afford one, it buys a healing potion before solving the next ad.                     | A test with 1 life and at least 50 gold produces a potion purchase. |
| BOT-06 | MUST         | Repeats from fetching ads **until lives reach 0**.                                                                 | The game ends only at game over or at the safety limit (BOT-07).    |
| BOT-07 | MUST         | Has a configurable safety limit on turns, to prevent endless loops.                                                | When the limit is reached, the game stops with a clear reason.      |
| BOT-08 | MUST         | Uses the state from each response (lives, gold, score, turn) as the source of truth and does not guess it locally. | State after each action matches the API response.                   |

It is kept in browser storage under its own key, apart from the saved game (WEB-15), so abandoning a game (WEB-17), game over, starting a new game and discarding a stale save never clear it. It comes from the player's own games, not from the API, whose `highScore` is always 0 (API-19). Stored data is validated before use, and invalid data is ignored. The app still works if storage is unavailable, and the high score then lasts until the page closes. Autopilot runs count when the app receives their stats: live events, the run list or the end summary. Runs that ended and were cleared (BOT-17) before the app saw them are not counted. The "New high score!" milestone (FUN-08) fires when the score passes a best that was above 0 before that quest. | After a game that ends on 300 points, the stats panel shows 300 as high score in the next game, also after a reload and after "Abandon game". A lower score in a later game leaves it at 300. Corrupt stored data shows 0. The saved game is removed on abandon, but the high score stays. An autopilot run that reaches 1100 raises it to 1100 on both screens. |

### Game feel (manual play)

Manual play is a game, not a view of the bot. The player makes every choice, and each choice is followed by a moment of anticipation and a clear payoff. None of this applies to autopilot.

## 13. Changing the stack

To switch technology, for example to Spring Boot for the bot or React for the web app:

1. Keep this document unchanged. It is the contract.
2. Re-implement the pieces in sections 3–5 in the new stack, with the same IDs.
3. Port the fake game API (TEST-03) first. Every other test depends on it.
4. Re-run the benchmark to confirm BOT-20 still holds.
5. Update the DOC-04 checklist and [PLAN.md](PLAN.md).
